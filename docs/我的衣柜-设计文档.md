# 我的衣柜设计文档

## 1. 模块目标

- 为 `moyu-miniapp` 增加“我的衣柜”模块，支持用户上传衣物照片、整理衣物信息、获取次日搭配建议、沉淀搭配记录。
- 后端实际允许接入图片识别模型与文本生成模型，但前端页面、按钮、提示语、接口展示字段中不出现 `AI`、`大模型`、`智能` 等敏感字样。
- 本期优先打通 MVP 闭环：上传 -> 异步整理 -> 手动修正 -> 明日搭配 -> 采纳记录。

## 2. 产品范围

### 2.1 本期包含

- 衣物照片上传
- 上传成功后立即进入衣物详情页
- 后端异步整理衣物信息
- 用户手动编辑衣物信息
- 衣柜列表与基础筛选
- 次日随机搭配建议
- 搭配采纳与搭配记录
- 天气缓存

### 2.2 本期不包含

- 批量上传
- 穿搭分享/社区
- 虚拟试衣
- 用户长期风格画像
- 多城市多日行程联动

## 3. 关键约束

- 图片上传成功后，接口必须快速返回，不能阻塞等待模型整理完成。
- 模型输出统一要求为 JSON，并由服务端二次校验。
- 天气信息必须做缓存，避免频繁访问第三方天气服务。
- 搭配前先做规则层预筛，再将候选衣物和天气信息交给模型生成建议。
- 前端文案统一使用“整理”“随机搭配”“明日参考”“搭配记录”等词。

## 4. 用户流程

### 4.1 衣物整理流程

1. 用户在小程序选择并上传衣物照片。
2. 后端完成文件上传后，立即创建衣物记录，状态为 `PENDING`。
3. 前端直接跳转衣物详情页，展示图片和“整理中”状态。
4. 后端异步执行衣物整理任务，完成后写回结构化信息。
5. 前端通过轮询或手动刷新获取整理结果。
6. 用户可手动修改名称、分类、颜色、季节、场景、描述等信息。

### 4.2 搭配建议流程

1. 用户进入“随机搭配”页面。
2. 后端读取次日天气缓存，没有缓存则请求天气服务并落库。
3. 后端基于天气和衣柜数据进行规则预筛。
4. 后端调用模型输出 1 到 3 套 JSON 结构的搭配方案。
5. 用户可切换“换一组”或“采纳这套”。
6. 用户采纳后，后端写入搭配记录。

### 4.3 搭配记录流程

1. 用户进入“搭配记录”页。
2. 查看日期、天气摘要、衣物组合、建议说明。
3. 可选补充反馈，如“偏热”“偏冷”“刚好”。

## 5. 前端设计

### 5.1 页面规划

- `pages/wardrobe/wardrobe`：衣柜首页
- `pages/wardrobe-item/wardrobe-item`：衣物详情页
- `pages/outfit/outfit`：随机搭配页
- `pages/outfit-history/outfit-history`：搭配记录页

### 5.2 页面结构

#### 我的衣柜

- 顶部统计：总件数、待整理、已整理
- 主按钮：上传衣物
- 最近衣物列表
- 快捷入口：随机搭配、搭配记录

#### 衣物详情页

- 图片预览
- 整理状态
- 可编辑字段：名称、一级分类、二级分类、颜色、季节、风格、场景、描述
- 操作按钮：保存

#### 随机搭配页

- 城市
- 次日天气摘要
- 当前搭配卡片
- 操作按钮：换一组、采纳这套

#### 搭配记录页

- 列表展示日期、天气、搭配标题、采纳时间

### 5.3 文案规范

#### 允许使用

- 正在整理衣物信息
- 已为你整理好这件衣物
- 随机搭配
- 明日参考穿搭
- 换一组
- 采纳这套
- 搭配记录

#### 禁止使用

- AI识别
- 大模型识别
- 智能分类
- 算法推荐
- 机器学习

## 6. 后端架构设计

### 6.1 模块拆分

- `WardrobeController`：衣物上传、列表、详情、编辑、归档
- `OutfitController`：随机搭配、刷新搭配、采纳搭配、搭配记录
- `WardrobeService`：衣物管理
- `WardrobeAsyncService`：异步整理任务调度
- `ClothingRecognitionService`：衣物整理结果生成与标准化
- `OutfitService`：搭配方案生成与落库
- `WeatherService`：天气缓存与天气快照获取

### 6.2 现有能力复用

- 小程序统一请求封装：`moyu-miniapp/utils/request.js`
- 后端文件上传与对象存储：`game-server/src/main/java/com/gamegroup/controller/FileController.java`
- 后端对象存储服务：`game-server/src/main/java/com/gamegroup/service/MinioService.java`
- 登录态注入：`@RequestAttribute("userId")`
- 通用 LLM 文本调用：`game-server/src/main/java/com/gamegroup/service/LlmService.java`

## 7. 数据库设计

### 7.1 t_wardrobe_item

- 衣物主表
- 关键字段：`user_id`、`image_url`、`name`、`category_level1`、`category_level2`、`color`、`season_tags`、`style_tags`、`summary_text`、`recognize_status`

### 7.2 t_wardrobe_item_detail

- 衣物扩展表
- 关键字段：`item_id`、`recognized_raw`、`confidence_score`

### 7.3 t_outfit_plan

- 搭配方案表
- 关键字段：`user_id`、`target_date`、`weather_condition`、`temperature_min`、`temperature_max`、`humidity`、`plan_title`、`plan_summary`、`plan_reason`、`status`

### 7.4 t_outfit_plan_item

- 搭配方案明细表
- 关键字段：`plan_id`、`wardrobe_item_id`、`item_role`

### 7.5 t_outfit_record

- 用户采纳记录表
- 关键字段：`user_id`、`plan_id`、`target_date`、`feedback`、`user_note`

### 7.6 t_weather_snapshot

- 天气缓存表
- 关键字段：`user_id`、`city`、`target_date`、`weather_condition`、`temperature_min`、`temperature_max`、`humidity`、`expire_time`

## 8. 状态定义

### 8.1 衣物整理状态

- `PENDING`：已上传待整理
- `PROCESSING`：整理中
- `SUCCESS`：整理完成
- `FAILED`：整理失败

### 8.2 搭配方案状态

- `GENERATED`：已生成
- `ADOPTED`：已采纳
- `DISMISSED`：已跳过或被刷新替换
- `EXPIRED`：已过期

## 9. 异步任务设计

### 9.1 上传接口执行链路

1. 小程序上传图片。
2. 服务端存储文件并生成 `imageUrl`。
3. 创建 `t_wardrobe_item` 记录，状态为 `PENDING`。
4. 接口立即返回 `itemId`、`imageUrl`、`recognizeStatus`。
5. 异步任务接管后续整理流程。

### 9.2 异步整理链路

1. 任务开始后将状态更新为 `PROCESSING`。
2. 调用识别服务生成结构化 JSON。
3. 服务端解析 JSON 并写回主表和扩展表。
4. 成功则状态更新为 `SUCCESS`。
5. 失败则状态更新为 `FAILED`，并记录错误信息。

## 11. 天气服务设计

- 输入：`userId`、`city`、`targetDate`
- 输出：天气现象、最高温、最低温、湿度、原始天气 JSON
- 缓存维度：`userId + city + targetDate`
- 缓存时长：建议 3 到 6 小时
- 降级策略：天气获取失败时优先使用最近缓存，没有缓存时返回兜底天气摘要

## 12. 搭配生成策略

### 12.1 规则层预筛

- 只选取 `ACTIVE + SUCCESS` 的衣物
- 高温优先轻薄单品
- 低温优先保暖等级较高单品
- 高湿优先透气性更好的衣物
- 雨天降低无防水属性鞋类优先级

### 12.2 模型层生成

- 输入：天气摘要、候选衣物列表、衣物描述文本
- 输出：标准 JSON 搭配建议
- 服务端负责解析、兜底和入库

## 14. MVP 验收标准

- 用户可上传图片并立即进入衣物详情页
- 后端可异步完成衣物整理并更新状态
- 用户可手动修改衣物信息
- 用户可查看衣柜列表
- 用户可获取次日随机搭配建议
- 用户可采纳搭配并写入记录
- 前端页面与提示文案不出现敏感词
- 天气信息具备缓存逻辑

## 15. 实施顺序

### 第一阶段

- 建表
- 衣柜上传接口
- 衣物详情/列表/编辑接口
- 异步整理骨架

### 第二阶段

- 天气缓存服务
- 随机搭配接口
- 搭配采纳与记录接口

### 第三阶段

- 接入正式天气来源
- 接入正式多模态识别能力
- 优化搭配候选与提示词

## 16. 原则应用说明

- `KISS`：先做单图上传、异步整理、单日搭配闭环。
- `YAGNI`：不提前做复杂画像和社区玩法。
- `DRY`：复用现有上传、鉴权、MinIO、LLM 调用能力。
- `SOLID`：识别、衣柜、天气、搭配、记录分服务实现，避免单体大类。
